# AGENTS.md

## Shape
- React Router 8 framework mode, `ssr: false`. Only `/{lang}`, `/{lang}/word`, `/{lang}/about`, `/{lang}/saved`
  are prerendered; word data loads in the browser from chunked JSON under `/data` (see README "How it works").
- PWA: `public/manifest.webmanifest` and a service worker generated by `scripts/postbuild.ts` from
  `scripts/sw.template.js` (precaches pages and app files, caches looked-up data). It only registers in builds.
- Deployed to Cloudflare Workers as static assets only (`wrangler.jsonc`), free plan: keep under 20,000 files
  (`scripts/postbuild.ts` enforces it).

## UI
- UI is built only from the published `@tinyrack/ui` package (pinned). Import components from
  `@tinyrack/ui/components/<name>` and add `@tinyrack/ui/components/<name>.css` to `app/app.css` after `core.css`.
- No raw `<p>`, `<h1>`…, `<button>`, `<input>`; no default Tailwind design utilities (`text-gray-500`, `p-4`, `border`).
  Use `TRText`, Tinyrack components and `*-tinyrack-*` utilities. `pnpm check:design` enforces this (CI too).
- Do not patch `node_modules`. Reusable gaps in `@tinyrack/ui` go upstream (tinyrack-net/design).

## Settings
- Every user setting lives in the URL: UI language in the path, `word`, `dicts`, `theme` in the query.
  Never store settings in localStorage/cookies. The only device storage is the two personal lists in
  `app/lib/history.ts` (recent and saved words). Read/write settings only through `useSettings()` in `app/lib/settings.ts`
  and build links with its `wordHref`/`pageHref`/`langHref` so settings carry over.
- Prerendered HTML can't see the query string: URL-dependent UI must render defaults until `useHydrated()`.

## Dictionaries are data
- `app/lib/dicts.ts` (`DICTIONARIES`) is the only place that names dictionaries: ids, languages (shown as the
  language pair on every card and in settings), names, descriptions, sources, licenses. App code, the build and the service worker iterate it; never add an `if`
  on a dictionary id, language or tag value anywhere else.
- A dictionary's data comes from a source module in `scripts/sources/` (contract: `scripts/lib/source.ts`), listed
  in `scripts/sources/index.ts`. Shared converters live in `scripts/lib/` (e.g. `wiktextract.ts`).
- The data build keeps dictionary content out of memory: sources append to spool files (`scripts/lib/core.ts`),
  and the writer assembles one dictionary at a time. Keep it that way; CI runners have ~16 GB.
- Never synthesize content. Converters copy each source into the neutral format of `app/lib/types.ts`
  (`DictPart`: entries, backlinks, sentence pairs): same entries, order, glosses, examples and tags; no merging
  across entries or sources, no summaries, ratings, rankings, guessed links, truncation or caps.
- The renderer (`app/components/DictEntryView.tsx`, `app/routes/word.tsx`) applies display rules to every
  dictionary equally.
- UI strings are per language in `app/locales/` (`en.ts` is the reference shape). Korean labels for source
  tags/POS come only from the 1:1 table `app/locales/tags.ko.ts`; unknown tags show verbatim.
- No compatibility shims for old URLs, data layouts or formats: change the code and the data together.
- `app/lib/fidelity.test.ts` checks built data against the raw source; extend it with the word behind a bug.
- `app/lib/preload.ts` mirrors the data paths of `data.ts` in plain JavaScript; `preload.test.ts` must stay green.
- Data URLs always go through `dataUrl()` (`app/lib/dataVersion.ts`): `/data/<content hash>/...`. Never fetch
  an unversioned data path; code and data of different builds must not meet in a browser cache.

## Commands
- `pnpm typecheck`, `pnpm check:design`, `pnpm test`, `pnpm build` (needs `data/site` from `pnpm fetch-data && pnpm build-data`).
- `pnpm preview` serves `build/client` with wrangler; restart it after every build.

## Workflow
- When asked to improve something, finish the job: implement, check (typecheck, design check, tests, build, a
  look in the browser), then commit, push to `main` and confirm the deploy succeeded.
- Keep README short: what the project is, its data and licenses, how to add a dictionary, how to develop.
  Details belong in code comments next to the code.
